# CheckAsync 순회 통합 비교 (2026-10-14)

**이번 순회 통합 후보는 운영 코드에 적용하지 않았습니다.** 일부 혼합 검사에서 CPU 시간이 줄었지만, 다른 자식을 시작하는 동안 앞쪽 Task가 완료되는 경우 대기용 Task를 불필요하게 만들면서 할당이 늘었습니다. [운영 ConditionGroup.cs](../../ConditionGroup.cs)의 별도 완료 확인 순회를 유지합니다.

## 비교한 변경

기준 구현은 모든 자식 Task를 시작하거나 재사용한 뒤 별도 루프로 IsCompleted를 확인합니다. 후보는 시작·재사용 루프에서 완료 여부를 누적하고, 뒤의 별도 루프를 제거합니다. 완료 여부를 찾은 이후에는 새 Task의 IsCompleted를 추가로 조회하지 않도록 짧은 평가를 사용했습니다.

변경 범위는 이 확인 방식뿐입니다. 호출 전후 목록 검증, 늦은 완료 전달, 실패 관찰, 취소와 중첩 정리, 버퍼 소유권은 유지했습니다. 기준과 후보의 ConditionGroup.cs를 별도 DLL로 컴파일하고 같은 프로세스에서 교대로 실행했습니다.

## 할당이 늘어나는 재현

첫 자식은 미완료 Task를 반환합니다. 후보는 이 시점에 미완료로 기록합니다. 마지막 자식의 CheckAsync 동기 부분이 첫 Task를 완료시키고, 마지막 자식 자신은 미완료 Task를 반환합니다. 나머지 자식들도 미완료인 상태입니다.

기준 구현은 모든 자식 시작 뒤 첫 Task의 완료를 발견해 WhenAny를 생략합니다. 후보의 누적 값은 미완료로 남아 WhenAny를 호출합니다. 완료 자체는 관찰되어 검사는 반환하지만 추가 할당과 처리 비용이 발생합니다.

아래 모형은 매 회 그룹을 시작·검사·종료하고 자식별 TCS를 생성합니다. 표의 전체 할당은 그 비용도 포함합니다. **후보와 기준의 차이가 추가 비용**이며, 기존 0 B 세션 재검사가 이 전체 값으로 바뀐다는 뜻은 아닙니다. 단위는 B/회입니다.

| 자식 수 | 기준 | 통합 후보 | 증가 |
|---|---:|---:|---:|
| 2 | 536 | 608 | +72 |
| 8 | 1,112 | 1,512 | +400 |
| 32 | 3,416 | 4,776 | +1,360 |
| 128 | 12,632 | 17,832 | +5,200 |

두 최종 실행에서 같은 할당을 확인했고 모든 배치의 할당 값이 동일했습니다. 완료 순서만으로 이 경로에 진입할 수 있으므로 실제 발생 빈도가 정해지지 않은 상태에서 기본 구현으로 채택하기는 어렵습니다.

나머지 모형의 할당은 두 구현이 동일했습니다. 모두 즉시 완료와 즉시 완료·대기 혼합은 0 B/회, 모두 대기 후 큐 완료는 N=1·8·32·128에서 각각 344·708·2,340·8,868 B/회였습니다. 평면 자동 재시작은 968 B/회, 중첩은 4,552 B/회였습니다.

새 검증 1개는 뒤쪽 자식 시작 중 앞쪽 검사가 완료되었을 때 즉시 반환하고, 아직 대기 중인 자식을 취소하지 않으며, 다음 라운드에서 완료된 자식만 재시작하고 종료 요청으로 남은 검사를 정리하는 동작을 확인합니다. 기존 검증에는 실패 관찰, 목록 변경, 취소·재진입, 중첩 정리와 참조 해제가 포함되어 있습니다.

## 재실행

저장소 루트에서 다음 명령을 사용합니다.

```powershell
./src/CrowRx.Trigger/verification/run.ps1 -Mode LoopComparison -Logging
# 패키지는 캐시에 있고 NuGet 접속이 안 되는 환경
./src/CrowRx.Trigger/verification/run.ps1 -Mode LoopComparison -Logging -Offline
```

이 모드는 운영 코드와 두 비교 구현의 검증을 실행하고 교대 벤치마크 결과를 verification/results/loops-paired.json에 저장합니다. 생성 결과는 Git에서 제외됩니다. 전체 검증·측정인 -Mode All에도 포함했습니다.

최종 두 결과는 verification/results/loops-final-first.json과 loops-final-repeat.json에 로컬 보관했습니다. 이전 탐색 측정은 큐 대기 모형에서 배치 첫 검사의 준비 할당 168 B를 포함했습니다. 최종 모형은 초기 CheckAsync와 큐 정리를 배치 시작에 수행해 이를 측정 구간에서 제외했습니다. 이 조정은 기준·후보에 동일하게 적용했으며, 위 표는 모두 최종 모형의 결과입니다.

측정 환경은 .NET 8.0.32, Windows 10.0.26300, x64, Workstation GC, Release, DOTNET_TieredCompilation=0입니다. 워밍업 2,000회, 배치당 4,000회, 7배치이며 GC.GetAllocatedBytesForCurrentThread로 측정했습니다. 무작업 0 B와 byte[64] 생성 88 B 양성 대조, 외부 스레드 등록 0회를 확인했습니다. 최초 대여·용량 증가·풀 보유 메모리와 Unity Editor·Mono·IL2CPP·Player 측정은 포함하지 않습니다.

기준 MVID는 a36700e1-4cb0-4871-be61-aa297d26faf3, 후보 MVID는 a8d098b0-a503-449d-9152-8b7fd8dbc575입니다. 결과 JSON에 각 실행의 식별자가 있습니다.

## 판단과 다음 후보

이번 단순 통합은 적용하지 않습니다. 완료를 누적한 값이 false일 때 추가로 재확인하면 이 할당 증가는 막을 수 있지만, 전부 대기 중인 경우에는 확인 작업이 늘어나므로 별도 비교가 필요한 다른 후보입니다.

다음 우선 후보는 AddConditions의 조건 수별 생성 비용을 먼저 측정하는 것입니다. 대량 구성 비용이 실제로 크면 기존 추가 훅·초기화·부분 성공 계약을 보존하는 별도 생성 API를 검토할 수 있습니다. 이번 작업에서 생성 API나 운영 검사 동작은 변경하지 않았습니다.
