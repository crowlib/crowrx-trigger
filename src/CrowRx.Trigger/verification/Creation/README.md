# ConditionGroup.Create 적용 결과 (2026-10-14)

[배열 입력의 null 제외 개수만큼 용량 확보](CAPACITY_CHANGE.md)를 운영 Create에 적용했습니다. 기본·로그 검증과 실제 공개 API 측정에서 할당 감소를 확인했습니다. 아래 용량 정책 미변경 및 최초 생성 API 수치는 이전 단계 기록입니다.

이후 [Create 목록 용량 정책](CAPACITY_COMPARISON.md)도 비교했습니다. null 제외 개수 확보는 GC 감소 후보로 유리했으나 추가 순회 비용이 있습니다. 이번 비교에서 운영 factory의 용량 정책은 변경하지 않았습니다.

후속으로 [배열 입력의 열거 할당 감소](ENUMERATION_CHANGE.md)를 적용했습니다. 현재 생성·열거 검증은 기본·로그 각각 24/24이며, 배열 입력의 Create는 아래 측정보다 32 B/회가 줄었습니다. 아래 18/18 및 CPU·할당 값은 생성 API 최초 적용 당시 기록입니다.

[ConditionGroup.Create](../../ConditionGroup.cs)를 구현했습니다. 입력을 복사하고 완성된 그래프를 한 번 검증한 뒤 새 미초기화 기본 그룹을 반환합니다. 기존 AddCondition·AddConditions의 구현은 변경하지 않았습니다.

콜백 작업이 없는 .NET 모형에서 평면 1,024개 새 구성은 기존 약 23–30 ms에서 Create 약 48–59 µs로 줄었습니다. 할당은 두 경로 모두 49,472 B/회였습니다. CPU 개선이며 객체 생성과 최종 목록의 할당을 없앤 변경은 아닙니다.

## 사용과 계약

```csharp
ConditionGroup group = ConditionGroup.Create(
    conditions,
    ConditionCombineType.And);
group.Initialize();
```

Listener에 전달하는 경우 기존 Listener 초기화 경로를 사용해도 됩니다.

- 입력을 한 번 열거하여 null이 아닌 자식 참조를 순서대로 새 List에 복사합니다. 입력 컬렉션을 반환 그룹의 목록으로 사용하지 않습니다.
- 반환 루트는 기본 ConditionGroup이며 IsInitialized·IsActivated는 false입니다. 자식의 기존 초기화·활성화 상태는 변경하지 않습니다.
- 자식 초기화와 추가 훅을 실행하지 않습니다. 자식 초기화는 이후 Initialize 또는 Listener 초기화에서 수행합니다.
- 중복 참조, 순환 및 중첩 그룹 내부 null을 전체 검증으로 거부합니다. 값으로 같은 조건이라도 서로 다른 참조는 허용합니다.
- And·Or 이외의 조합은 입력 열거 전에 ArgumentOutOfRangeException으로 거부합니다.
- 입력 열거 또는 검증 실패 시 새 그룹을 반환하지 않습니다. 입력 열거자가 수행한 외부 부수 효과는 호출자가 관리합니다.

null 입력·빈 입력·null 원소만 있는 입력은 비어 있는 새 목록을 가진 그룹을 반환합니다. IsValid는 false이고 만족값은 기존 빈 목록의 조합 규칙을 따릅니다: 기본 AND는 true, OR는 false입니다. 만족값만으로 빈 그룹을 유효한 조건으로 간주하지 않습니다.

기존 그룹에 추가하거나 ConditionGroupShareTarget 같은 파생 루트를 구성할 때는 기존 추가 API를 사용합니다. 새 factory는 파생 루트의 설정 훅을 우회해 그 타입을 생성하는 API가 아닙니다. 자식으로 들어오는 중첩·파생 조건 자체는 검증 범위에서 지원합니다.

## 기존 경로와의 차이

기존 AddConditions는 원소마다 추가 훅·필요한 초기화를 수행하고 그 뒤 그래프를 재검증합니다. 중간 실패 시 앞선 추가가 남습니다. Create는 그룹을 반환하기 전에 입력 수집과 검증을 끝내며 생성 중 훅·초기화를 수행하지 않습니다.

특히 기존 초기화된 부모에 추가하는 경로에서는 해당 자식을 목록에 넣기 전에 초기화합니다. Create 후 Initialize 경로에서는 완성된 목록이 이미 부모에 존재합니다. 사용자 콜백이 관찰하는 상태와 실행 순서는 다르므로 기존 API의 대체 구현으로 바꾼 것은 아닙니다.

## 동일 프로세스 교대 비교

두 경로 모두 입력 배열·자식·루트를 새로 만들고 같은 수의 자식을 가진 결과를 만듭니다. 같은 라이브러리·같은 벤치마크 조건 타입을 사용하며 7배치에서 실행 순서를 교대했습니다. 별도 프로세스에서 한 번 더 실행했습니다.

미초기화 모형은 생성 결과만 비교합니다. 초기화 모형은 기존 경로에서 빈 부모를 초기화한 뒤 추가하고, factory에서는 그룹을 만든 뒤 초기화합니다. 최종 초기화 상태는 같지만 콜백 순서가 다릅니다. 사용자 콜백은 벤치마크에서 작업을 하지 않습니다.

중첩 N은 직접 자식 그룹 N개이며 각 그룹에 말단 조건 4개가 있습니다. 이 하위 그룹 구성에는 양쪽 모두 기존 AddConditions를 사용하여 루트 생성 경로만 비교합니다. 중첩 총 노드 수는 1+5N개입니다.

## 측정 한계

큰 기존 구성은 오래 걸리므로 반복 횟수를 줄이고, 빠른 Create는 더 많이 반복했습니다. 작업당 정규화된 시간이며 횟수는 JSON에 기록합니다. Create 배치에는 자연스럽게 발생하는 Gen0 수집이 더 많이 포함될 수 있습니다. 예를 들어 1,024개 평면 모형은 기존 배치당 3회, Create 512회였고 7배치 합계 Gen0 수집은 기존 0회·Create 7회였습니다. 이 숫자를 두 경로의 작업당 할당 차이라고 해석하지 않습니다.

N 직접 자식, S=N×(평면 1, 중첩 5)일 때 기존 반복 횟수는 clamp(524,288/(N×S), 3, 16,384), Create는 clamp(524,288/S, 32, 16,384)입니다. 워밍업은 각각 clamp(32,768/(N×S), 2, 128), clamp(32,768/S, 2, 128)이며 정수 나눗셈을 사용합니다.

호스트 속도와 캐시·객체 해시 분포에 따른 변동이 있습니다. 첫 실행과 재측정의 CPU 차이도 있었으므로 특정 배수를 일반적인 게임 성능으로 제시하지 않습니다. 재측정 배치 범위는 다음과 같습니다.

| 작업 | 기존 µs 범위 | Create µs 범위 |
|---|---:|---:|
| 평면 1024 | 24,031.033–32,989.167 | 50.05–140.264 |
| 중첩 512 | 32,252.933–33,628.867 | 1,341.55–1,400.43 |

측정 환경은 .NET 8.0.32, Windows 10.0.26300, x64, Workstation GC, Release, DOTNET_TieredCompilation=0입니다. GC.GetAllocatedBytesForCurrentThread로 할당을 측정했고 무작업 0 B·byte[64] 88 B 대조군을 확인했습니다. 풀 최초 대여·용량 증가 비용은 워밍업에서 제외됩니다. Unity Editor·Mono·IL2CPP·Player 결과는 아닙니다.

## 실행과 기록

저장소 루트에서 실행합니다.

```powershell
# 기존 검증과 생성 API 검증
./src/CrowRx.Trigger/verification/run.ps1 -Mode Tests -Logging

# 생성 API 검증과 교대 벤치마크
./src/CrowRx.Trigger/verification/run.ps1 -Mode Creation -Logging

# 패키지는 캐시에 있고 NuGet 접속이 안 되는 환경
./src/CrowRx.Trigger/verification/run.ps1 -Mode Creation -Logging -Offline
```

-Mode Benchmarks와 -Mode All에도 생성 비교를 포함했습니다. 기본 검증 실행은 기존 수명 검증과 생성 API 검증을 함께 실행합니다. 비교 소스는 [Benchmark.cs](Benchmark.cs)이며 공개 사용법은 [Readme.md](../../Readme.md)에 추가했습니다.

결과 JSON은 verification/results/creation.json, 별도 재측정은 creation-repeat.json입니다. 생성물과 패키지는 Git 제외 대상이며 코드는 아직 커밋하지 않았습니다. 라이브러리 MVID는 d2e61df8-3fa4-4445-a6c8-920edb64cf5e이며 각 결과에 기록됩니다.

전체 트리를 여러 단계에서 만들면서 각 단계의 하위 그래프를 다시 검증하는 작업까지 한 번의 선형 순회로 만든 변경은 아닙니다. 단일 기본 루트의 수집·검증 비용을 줄이는 API입니다.
