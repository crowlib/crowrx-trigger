# Create 목록 용량 비교 (2026-10-14)

비교 이후 null 제외 개수 확보를 운영 코드에 적용했습니다. [적용 결과와 실제 공개 API 재측정](CAPACITY_CHANGE.md)을 참고하세요. 아래는 선택 전 모형 비교 기록이며 운영 미변경 설명도 당시 상태입니다.

**GC 감소를 우선한다면 null이 아닌 원소를 먼저 센 뒤 그 수만큼 확보하는 방식이 가장 일관된 후보입니다.** 배열 길이만큼 확보하는 방식은 null이 많을 때 현재 구현보다 할당과 보유 용량이 커졌습니다. 개수를 먼저 세는 방식은 추가 순회의 CPU 비용이 있으며, 모든 입력에서 더 빠르다고 결론 내리지 않습니다.

이번 작업은 비교용 모형·검증·실행 경로를 추가한 것입니다. 운영 ConditionGroup.Create의 구현은 이번 비교에서 변경하지 않았습니다. 다음 적용 후보는 직접 배열 입력의 null 제외 개수 확보이며, 다른 IEnumerable 경로와 AddConditions는 현재 구현을 유지하는 범위입니다.

## 비교한 방식

| 방식 | 목록 초기 용량 | 배열 순회 |
|---|---|---|
| current_model | 0, List의 성장에 맡김 | 수집 1회 |
| array_length | 배열 길이 | 수집 1회 |
| nonnull_count | null이 아닌 원소 개수 | 개수 확인 1회 + 수집 1회 |
| production | 현재 공개 ConditionGroup.Create | 대조용 실제 호출 |

세 모형은 인스턴스 필드가 없는 파생 그룹에서 현재 운영 그래프 검증을 호출합니다. 참조 순서, null 생략, 미초기화·비활성 반환 및 전체 그래프 한 번 검증을 유지했습니다. 운영 factory는 현재 모형의 할당량과 Capacity가 일치하는지 확인하는 네 번째 경로입니다. 후보에서 추가한 용량 계산만 비교하며 전체 공개 API를 교체한 빌드의 측정은 아닙니다.

## 할당량과 최종 용량

단위는 B/회이며 괄호는 반환 목록의 Capacity입니다. 미리 준비한 평면 배열과 자식을 사용하므로 아래 값에는 입력 배열·자식 생성이 포함되지 않습니다. 새 그룹·목록·목록 배열 및 그래프 검증은 측정 구간에 포함됩니다. 앞선 전체 생성 비교의 49,440 B/회와 측정 구간이 다릅니다.

| 배열 길이 | 요청 null 비율 | 실제 자식 수 | 현재 | 배열 길이 확보 | null 제외 개수 확보 |
|---|---|---|---|---|---|
| 1 | 0% | 1 | 136 (4) | 112 (1) | 112 (1) |
| 1 | 50% | 1 | 136 (4) | 112 (1) | 112 (1) |
| 1 | 90% | 1 | 136 (4) | 112 (1) | 112 (1) |
| 8 | 0% | 8 | 224 (8) | 168 (8) | 168 (8) |
| 8 | 50% | 4 | 136 (4) | 168 (8) | 136 (4) |
| 8 | 90% | 1 | 136 (4) | 168 (8) | 112 (1) |
| 32 | 0% | 32 | 656 (32) | 360 (32) | 360 (32) |
| 32 | 50% | 16 | 376 (16) | 360 (32) | 232 (16) |
| 32 | 90% | 4 | 136 (4) | 360 (32) | 136 (4) |
| 128 | 0% | 128 | 2,240 (128) | 1,128 (128) | 1,128 (128) |
| 128 | 50% | 64 | 1,192 (64) | 1,128 (128) | 616 (64) |
| 128 | 90% | 13 | 376 (16) | 1,128 (128) | 208 (13) |
| 1024 | 0% | 1024 | 16,648 (1024) | 8,296 (1024) | 8,296 (1024) |
| 1024 | 50% | 512 | 8,432 (512) | 8,296 (1024) | 4,200 (512) |
| 1024 | 90% | 103 | 2,240 (128) | 8,296 (1024) | 928 (103) |

실제 null 수는 floor(배열 길이 × 요청 비율 / 100)이며 분산 배치합니다. 따라서 길이 1에서는 세 요청 비율 모두 실제 null이 없고, 길이 1,024의 90% 모형에는 실제 자식 103개가 남습니다.

- 길이 1,024·null 없음: 16,648 → 8,296 B/회로 8,352 B가 감소합니다. 반환 Capacity는 두 방식 모두 1,024이며 감소한 것은 성장 과정의 중간 배열 할당입니다.
- 길이 1,024·실제 자식 512개: 개수를 먼저 세면 8,432 → 4,200 B/회, Capacity 512를 유지합니다. 배열 길이 방식은 Capacity 1,024를 보유합니다.
- 길이 1,024·실제 자식 103개: 개수를 먼저 세면 2,240 → 928 B/회, Capacity 128 → 103입니다. 배열 길이 방식은 8,296 B/회와 Capacity 1,024로 오히려 커집니다.
- 현재 목록이 한 번만 할당되고 Capacity가 정확한 작은 사례는 감소가 없었습니다. 길이 8·실제 자식 4개와 길이 32·실제 자식 4개는 현재와 개수 확보 모두 136 B/회입니다.

Capacity는 보유 원소 슬롯 수이며 작업 전체의 생존 메모리 바이트를 직접 측정한 수치는 아닙니다. 그래프 검증 풀이 워밍업된 결과로 최초 풀 생성이나 용량 증가를 포함하지 않습니다.

## CPU 비용과 선택

다음은 길이 1,024에서 각 프로세스의 배치 중앙값입니다. 단위는 µs/회이며 첫 실행 / 재실행 순서입니다.

| 요청 null 비율 | 실제 자식 수 | 현재 모형 | 배열 길이 확보 | null 제외 개수 확보 |
|---|---|---|---|---|
| 0% | 1024 | 29.07 / 32.34 | 27.07 / 30.84 | 27.77 / 30.19 |
| 50% | 512 | 14.69 / 16.88 | 14.16 / 17.30 | 14.79 / 21.64 |
| 90% | 103 | 3.86 / 4.91 | 4.02 / 5.71 | 4.25 / 5.62 |

null이 없는 대량 입력에서 개수 확보는 두 실행 모두 현재 모형보다 낮은 중앙값을 보였습니다. 그러나 추가 순회가 모든 경우에 CPU 이득을 주지는 않습니다. 자식이 103개인 사례는 4.25 / 5.62 µs로, 현재 3.86 / 4.91 µs보다 약 10 / 14% 높았습니다. 50% 사례도 첫 실행은 비슷했으나 재실행은 개수 확보가 더 높았습니다.

배치 범위가 겹치고 실행 간 CPU 변동이 있어 이 수치를 일반적인 성능 개선율로 제시하지 않습니다. 정책 선택과 검증용 생성 helper의 호출도 포함되어 실제 운영 패치의 정확한 개선율은 적용 후 다시 확인해야 합니다.

선택 기준은 다음과 같습니다.

- GC 감소와 불필요한 목록 용량 억제가 우선이면 nonnull_count를 권합니다. 측정한 모든 입력에서 현재보다 할당이 적거나 같고, 최종 Capacity는 실제 자식 수입니다.
- CPU가 우선이고 실제 입력에서 null이 거의 없다면 array_length를 검토할 수 있습니다. 일반 null 허용 계약에 그대로 적용하는 것은 권하지 않습니다.
- 긴 배열에 실제 자식이 아주 적고 생성 할당이 병목이 아니라면 현재 방식 유지도 타당합니다. 이번 결과만으로 추가 순회를 항상 적용해야 한다고 보지는 않습니다.

## 검증과 측정 조건

| 확인 | 결과 |
|---|---|
| 현재 생성·열거 검증 | 24/24 통과 |
| 용량 모형 계약 검증 | 네 경로 각각 32개 시나리오 통과 |
| Release Creation 프로젝트 빌드 | 경고 0개·오류 0개 |
| 결과 행 | 두 프로세스 각각 68개, 할당 값 전체 일치 |
| 배치별 할당 | 모든 행에서 최솟값 = 최댓값 |
| 현재 모형의 할당량·Capacity | 실제 공개 factory와 15개 입력 조합에서 일치 |
| 무작업 / byte[64] 대조 | 0 / 88 B/회 |

32개 시나리오는 길이 0·1·8·32·128·1,024와 null 비율 0·50·90·100%의 24개 조합, 그리고 null 입력·AND/OR 빈 그룹, 잘못된 결합 값, 독립 복사·초기화 지연, 기존 자식 상태, 중복 자식, 중첩 공유, 순환, 중첩 null의 8개 계약 시나리오입니다. 참조 순서와 입력 소유권, 실패 때 중첩 입력을 변경하지 않는 점도 확인합니다.

Windows x64, .NET 8.0.32, workstation GC, Release, DOTNET_TieredCompilation=0입니다. GC.GetAllocatedBytesForCurrentThread로 측정합니다. 네 방식의 순서를 회전하는 8배치로 각 방식은 각 실행 위치에 두 번 배치됩니다. 워밍업은 128회, 길이 1·8·32는 배치당 16,384회, 길이 128은 4,096회, 길이 1,024는 512회입니다. 대조군은 배치당 100,000회입니다. 강제 GC는 측정 구간 밖에서 실행했습니다.

두 실행의 운영 라이브러리 MVID는 7384e5b1-e4a8-436b-a223-2f2c86ea9d3e로 같습니다. 이번에는 운영 수명 검증 전체나 로그 심볼 검증을 다시 실행하지 않았습니다. 이전 69/69·72/72은 배열 열거 개선 단계의 결과입니다. 캐시된 패키지와 Offline 옵션을 사용해 이번 복원 호출의 NuGet 감사를 생략했습니다. Unity Editor·Mono·IL2CPP·Player 측정은 수행하지 않았습니다.
