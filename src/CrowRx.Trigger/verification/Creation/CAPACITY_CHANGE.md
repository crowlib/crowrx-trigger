# Create 배열 입력의 목록 용량 확보 적용 (2026-10-14)

ConditionGroup.Create의 직접 배열 입력에서 null이 아닌 원소 수를 먼저 세고 new List<ICondition>(count)로 최종 목록 용량을 확보하도록 적용했습니다. 목록 성장 과정의 중간 배열 할당을 줄이면서 null이 많은 입력의 과도한 용량 확보를 피합니다.

.NET 재측정에서 미리 준비한 자식 1,024개를 전달하는 실제 공개 Create는 16,648 → 8,296 B/회로 줄었습니다. 입력 배열·자식 생성까지 포함한 새 평면 그룹 전체 구성은 49,440 → 41,088 B/회였습니다. 두 값은 측정 구간이 다릅니다.

## 변경과 유지한 계약

[ConditionGroup.Create](../../ConditionGroup.cs)의 ICondition[] 분기만 용량 정책을 바꿨습니다.

1. null이 아닌 원소 수를 센 뒤 목록 인스턴스를 한 번 생성합니다.
2. 같은 배열에서 자식 참조를 기존 순서로 복사합니다. 원소 초기화나 추가 훅은 실행하지 않습니다.
3. 기존처럼 완성된 그래프를 한 번 검증하고 새 기본 그룹을 반환합니다.

비배열 IEnumerable은 Count를 읽거나 먼저 열거하지 않고 기존 foreach로 한 번 수집합니다. null 입력은 새 빈 목록을 가진 미초기화·비활성 그룹을 반환합니다. 결합 값 검증은 입력 처리 전이며 null 생략, 참조 동일성, 입력과 반환 목록의 독립성, 그래프 오류 처리도 유지했습니다.

AddCondition·AddConditions 및 그 이후의 운영 메서드는 이전 단계의 소스와 동일합니다. 공변 배열도 배열 분기에서 처리합니다. 배열 수집 중에는 사용자 콜백을 호출하지 않으므로 개수 확인과 복사 사이에 초기화·추가 훅이 개입하지 않습니다. 라이브러리의 동일 실행 컨텍스트 호출 계약은 유지됩니다.

## 실제 공개 API의 할당량

입력 배열·자식은 측정 전에 준비했습니다. 새 그룹과 목록, 목록 배열 및 그래프 검증은 측정 구간에 포함합니다. 단위는 B/회입니다.

| 배열 길이 | 요청 null 비율 | 실제 자식 수 | 이전 → 적용 후 할당 | 이전 → 적용 후 Capacity |
|---|---|---|---|---|
| 1 | 0% | 1 | 136 → 112 | 4 → 1 |
| 8 | 0% | 8 | 224 → 168 | 8 → 8 |
| 32 | 0% | 32 | 656 → 360 | 32 → 32 |
| 128 | 0% | 128 | 2,240 → 1,128 | 128 → 128 |
| 1024 | 0% | 1024 | 16,648 → 8,296 | 1024 → 1024 |
| 1024 | 50% | 512 | 8,432 → 4,200 | 512 → 512 |
| 1024 | 90% | 103 | 2,240 → 928 | 128 → 103 |

요청 null 수는 floor(배열 길이 × 비율 / 100)으로 생성했습니다. 90% 모형의 길이 1,024에는 실제 자식 103개가 남습니다. 반환 Capacity는 생성 시점의 슬롯 수이며 전체 생존 메모리 바이트를 측정한 값은 아닙니다.

비교의 15개 입력 조합 모두 실제 Create의 할당·Capacity가 null 제외 개수 모형과 일치했습니다. 68개 행의 배치별 할당도 안정적이었고 무작업 0 B/회·byte[64] 88 B/회 대조를 통과했습니다.

벤치마크의 current_model 이름은 과거 기록에 남겨두고 현재 실행에서는 growth_model로 바꿨습니다. 이 모형은 적용 전의 목록 성장 정책을 보존합니다. production은 실제 변경된 API이며, 자동 대조도 nonnull_count와 일치하는지 검사하도록 바꿨습니다.

## 전체 구성 및 비배열 경로 확인

기존 Creation 벤치마크 48개 행을 적용 전 기록과 비교했습니다.

| 경로 | 이전 → 적용 후 |
|---|---|
| 새 평면 그룹, 자식 1,024개, 초기화 전후 모두 | 49,440 → 41,088 B/회 |
| 새 중첩 그룹, 직접 자식 그룹 512개, 초기화 전후 모두 | 160,008 → 155,776 B/회 |
| 기존 AddConditions로 만드는 전체 구성 | 모든 행의 기존 할당 유지 |
| 무작업 / byte[64] 대조 | 0 / 88 B/회 유지 |

Create의 각 조건 수에서 목록 성장 중간 배열 제거분만큼 줄었습니다. 중첩 모형의 자식 그룹은 기존 추가 경로로 구성하므로 이 단계의 감소는 최상위 Create 목록에서 발생합니다. 입력 객체 생성까지 없앤 최적화는 아닙니다.

Enumeration 집중 비교 20개 행도 다시 확인했습니다. 워밍업된 배열 AddConditions는 자식 수 1·8·32·128에서 0 B/회, 같은 배열을 감싼 IEnumerable은 32 B/회를 유지했습니다. Create의 배열 경로는 각각 112·168·360·1,128 B/회, 비배열 래퍼는 기존 168·256·688·2,272 B/회였습니다.

현재 Create의 배열·래퍼 차이에는 열거자뿐 아니라 이번 목록 성장 정책 차이도 포함됩니다. 벤치마크 메타데이터의 설명을 이에 맞게 수정했습니다. 비배열 입력의 실제 생성·열거·Dispose 계약은 기존 24개 검증에서도 통과했습니다.

## CPU 비용

길이 1,024에서 이번 동일 프로세스의 배치 중앙값은 다음과 같습니다. 단위는 µs/회입니다.

| 요청 null 비율 | 적용 전 정책 모형 | 적용 후 실제 Create | 실제 Create 배치 범위 |
|---|---|---|---|
| 0% | 40.19 | 42.69 | 40.72–45.63 |
| 50% | 20.79 | 20.56 | 19.72–24.36 |
| 90% | 5.01 | 5.77 | 5.03–6.01 |

정책 모형은 필드 없는 파생 그룹과 helper를 사용하므로 실제 적용 전 factory의 정확한 CPU 대조 구현은 아닙니다. 이전 프로세스와 현재 프로세스 사이에도 절대 시간 변동이 있습니다. 이번 데이터로 용량 변경의 CPU 개선율을 확정하지 않습니다.

이 변경은 GC 감소를 선택한 결과입니다. 배열 한 번을 더 순회하므로 입력 길이가 길고 실제 자식이 적은 경우 추가 CPU 비용이 있습니다. 이전 모형 비교에서 자식 103개는 약 0.4–0.7 µs의 추가 비용을 보였고 이번 실제 API도 그 비용을 고려해야 합니다. 실제 사용의 실행 빈도와 플랫폼에서 CPU·GC 균형을 확인할 수 있습니다.

./src/CrowRx.Trigger/verification/run.ps1 -Mode Creation -Offline
