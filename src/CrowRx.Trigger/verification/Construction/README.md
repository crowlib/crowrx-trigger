# AddConditions 구성 비용 측정 (2026-10-14)

후속으로 [배열 입력 열거 개선](../Creation/ENUMERATION_CHANGE.md)을 적용했습니다. 현재 워밍업된 AddConditions의 배열 입력은 0 B/회이며, 아래 32 B/회 및 전체 구성 측정은 개선 전 기록입니다. 같은 63개 항목의 할당 차이를 후속 문서에 기록했습니다.

이후 별도 ConditionGroup.Create를 구현했습니다. [구현·검증·기존 경로와의 비교](../Creation/README.md)에서 대량 구성 CPU 감소를 확인했습니다. 아래는 새 API 구현 전 AddConditions 비용 측정 기록입니다.

대량 구성 모형에서 반복 그래프 검증의 CPU 비용이 뚜렷했습니다. 새 평면 그룹의 조건 512개 구성은 약 5.7–5.8 ms, 1,024개는 약 23 ms였습니다. 부모를 먼저 초기화한 뒤 새 조건 1,024개를 추가하면 약 34 ms였습니다. 객체를 재사용한 모형도 비슷한 시간대를 보여, 이 규모에서는 객체 생성보다 반복 검증이 주요 비용이라는 근거가 됩니다.

운영 코드와 공개 API는 변경하지 않았습니다. 벤치마크와 실행 경로를 추가하고 두 프로세스에서 재측정했습니다. Unity 소비 프로젝트가 없는 현재 단계의 .NET 호스트 기준이며 실제 게임의 병목을 확인한 결과는 아닙니다.

## 측정한 경로

| 경로 | 측정 구간 |
|---|---|
| fresh | 부모·입력 배열·자식을 새로 만들고 AddConditions 호출. 초기화된 부모 모형은 부모 Initialize와 새 자식 초기화도 포함 |
| reuse | 준비된 부모의 자식 목록을 Clear하고 같은 자식 인스턴스를 다시 추가. 목록 용량과 검증 풀은 워밍업 상태 |
| validate | 완성된 그룹에 ValidateConditionGraph 한 번 호출하는 참고 경로. 실제 구성 API와 같은 일을 하는 경로는 아님 |
| single_add | 배열을 직접 foreach하여 AddCondition을 반복 호출. 입력 열거 방식의 비용을 비교 |

초기화된 부모의 reuse 모형은 워밍업에서 이미 초기화된 자식을 다시 추가합니다. 따라서 새 자식의 초기화 비용까지 보려면 fresh 결과를 사용해야 합니다. 자식의 사용자 초기화 콜백·추가 훅은 벤치마크에서 별도 작업을 수행하지 않습니다. 실제 콜백의 작업량은 측정에 포함하지 않았습니다.

평면 N은 말단 자식 N개입니다. 중첩 N은 루트의 직접 자식 그룹 N개이며, 각 그룹이 말단 조건 4개를 가집니다. 중첩 모형의 총 노드는 루트 포함 1+5N개이므로 같은 N의 평면과 같은 노드 수가 아닙니다.

## 새 그룹 구성

CPU는 배치 중앙값 µs/회, 할당은 B/회입니다. 첫 실행과 재측정의 할당 값은 모든 항목에서 동일했고, fresh의 초기화 전후도 동일한 할당을 보였습니다.

### 평면

| 직접 자식 N | 총 노드 | 미초기화 1차 µs | 미초기화 재측정 µs | 초기화 1차 µs | 초기화 재측정 µs | 할당 B |
|---|---:|---:|---:|---:|---:|---:|
| 1 | 2 | 0.361 | 0.651 | 0.383 | 0.644 | 224 |
| 8 | 9 | 3.669 | 5.548 | 3.866 | 5.826 | 536 |
| 32 | 33 | 33.698 | 47.788 | 33.096 | 48.437 | 1,736 |
| 128 | 129 | 392.578 | 578.422 | 387.238 | 583.291 | 6,392 |
| 512 | 513 | 5,810.2 | 8,769.3 | 5,705.933 | 8,719.733 | 24,872 |
| 1024 | 1025 | 22,811.4 | 33,970.333 | 22,975.9 | 34,081.733 | 49,472 |

512→1,024개에서 미초기화 fresh 시간은 재측정 기준 4.027배, 재사용 경로는 3.881배였습니다. 조건 수가 두 배일 때 시간이 대략 네 배로 증가한 결과는 현재 반복 검증 구조의 O(N²) 증가와 부합합니다.

큰 그룹의 배치는 반복 횟수가 작으므로 미세한 차이에 의미를 부여하지 않습니다. 재측정의 1,024개 fresh 배치 범위는 아래와 같습니다.

| 부모 상태 | 중앙값 ms | 배치 범위 ms |
|---|---:|---:|
| 미초기화 부모 | 22.976 | 22.704–23.242 |
| 초기화된 부모 | 34.082 | 33.51–34.566 |

|---|---:|---:|---:|---:|---:|---:|
| 1 | 6 | 2.542 | 3.278 | 2.612 | 3.306 | 520 |
| 8 | 41 | 25.85 | 33.128 | 26.484 | 34.239 | 2,904 |
| 32 | 161 | 189.567 | 255.526 | 186.743 | 262.163 | 11,208 |
| 128 | 641 | 2,040.95 | 3,077.5 | 2,090.333 | 3,054.233 | 44,280 |
| 512 | 2561 | 30,661.533 | 45,601.133 | 30,523.967 | 45,455.3 | 176,424 |

직접 자식 그룹 512개, 말단 조건 2,048개인 모형은 미초기화 fresh 약 30.5 ms, 초기화된 부모 약 45.5 ms였습니다. 자식 그룹과 그 안의 조건을 만드는 비용도 포함된 수치입니다.

## 반복 검증과 객체 생성의 구분

아래는 재측정 CPU 중앙값 µs/회입니다. 재사용 경로는 32 B/회, 완성 그래프 한 번 검증은 0 B/회였습니다.

| 구조·직접 자식 수 | 재사용·미초기화 부모 | 재사용·초기화된 부모 | 완성 그래프 한 번 검증 |
|---|---:|---:|---:|
| 평면 8 | 3.509 | 5.308 | 0.292 |
| 평면 128 | 374.709 | 564.694 | 2.764 |
| 평면 512 | 5,605.433 | 8,292.833 | 10.782 |
| 평면 1024 | 21,756.467 | 32,629.9 | 21.719 |
| 중첩 8 | 10.27 | 15.496 | 0.96 |
| 중첩 128 | 1,733.433 | 2,622.383 | 14.016 |
| 중첩 512 | 28,123.533 | 41,950.067 | 56.739 |

예를 들어 평면 1,024개는 새 그룹 약 23 ms, 재사용 약 21.8 ms였고 완성 그래프의 검증 한 번은 약 21.7 µs였습니다. 검증을 반복하는 구조가 큰 구성 비용을 만든다는 근거입니다. 한 번 검증 결과는 일괄 생성 API의 처리 시간이나 보장할 수 있는 개선 배수가 아닙니다. 실제 API에는 입력 수집·목록 구성·훅·초기화·실패 처리 비용과 계약이 추가됩니다.

현재 AddCondition은 추가 전과 OnConditionAdding 후에 그래프를 검증하고, 부모가 초기화됐다면 자식 Initialize 후에도 다시 검증합니다. 콜백이 그래프나 부모 상태를 바꿀 수 있어 이 재검증에는 정확성 목적이 있습니다.

훅이 그래프를 바꾸지 않는 평면 모형에서 k번째 추가의 검증 대상은 부모 포함 k+1개입니다. 미초기화 부모는 2회씩 검사하므로 전체 방문량은 2×Σ(k+1)=N²+3N입니다. 초기화된 부모는 3회씩 검사하므로 1.5N²+4.5N입니다. 이 계산은 단순 모형의 구조 분석이며 사용자 콜백이 실행되는 모든 그래프에 그대로 적용하는 공식은 아닙니다.

## 작은 할당 개선 후보

워밍업된 평면 그룹에서 입력 배열을 AddConditions에 전달하면 32 B/회였고, 같은 배열을 직접 순회하며 AddCondition을 호출하면 0 B/회였습니다.

| N | AddConditions µs | 직접 AddCondition 반복 µs | AddConditions B | 직접 반복 B |
|---|---:|---:|---:|---:|
| 8 | 3.509 | 5.346 | 32 | 0 |
| 128 | 374.709 | 403.447 | 32 | 0 |
| 1024 | 21,756.467 | 21,900.967 | 32 | 0 |

현재 AddConditions는 배열 입력도 IEnumerable<ICondition>로 순회합니다. 입력 열거 방식을 구분하는 작은 개선 후보가 있습니다. 두 방식 모두 매 원소의 전체 그래프 검증은 유지하므로 큰 구성의 O(N²) CPU 비용은 해결하지 못합니다. 시간 차이도 항상 한쪽이 빠르다는 결과는 아닙니다.

배열 입력만 분기해서 순회하더라도 입력 순서, null 처리, 콜백 도중 뒤쪽 원소 변경, 예외와 부분 성공 동작을 확인해야 합니다. 이 최적화는 이번 작업에서 적용하지 않았습니다.

## 판단

조건 수가 수십 개이고 구성이 드물다면 현재 안전한 경로를 유지할 수 있습니다. 수백~수천 개를 자주 구성하는 사용에서는 반복 검증을 줄이는 별도 생성 API를 검토할 근거가 충분합니다.

다음 설계 후보는 새 미초기화 기본 그룹을 구성하는 경로입니다. 입력을 한 번 수집하고 전체 그래프를 검증한 뒤 반환하는 방식은 콜백 없는 구성 단계에서 O(N) 순회로 만들 여지가 있습니다. 구체적인 이름·시그니처·성능은 아직 정하거나 구현하지 않았습니다.

기존 AddConditions를 바꾸어 훅·초기화 뒤 검증을 생략하는 방식은 권하지 않습니다. 다음 사항을 먼저 계약으로 정해야 합니다.

- 추가 훅과 초기화를 언제 수행하는지, 기본 그룹 이외의 파생 타입을 지원하는지.
- null 입력·null 원소, 중복·순환 참조 및 열거 실패의 처리.
- 실패 시 전체 생성이 실패하는지, 기존 API의 부분 성공을 유지하는지.
- 반환 전 임시 그룹·목록이 사용자 코드에 노출되는지.

Target 공유 그룹은 추가 훅이 설정을 전달하므로 기본 그룹용 구성 경로로 우회하지 않습니다. 새 생성 API의 조건에 맞지 않는 사용은 기존 AddConditions를 계속 사용해야 합니다.

## 재실행 및 측정 조건

저장소 루트에서 다음 명령을 사용합니다.

```powershell
./src/CrowRx.Trigger/verification/run.ps1 -Mode Construction
# 패키지는 캐시에 있고 NuGet에 접속할 수 없는 환경
./src/CrowRx.Trigger/verification/run.ps1 -Mode Construction -Offline
```

- [벤치마크 소스](Program.cs)
- [벤치마크 프로젝트](Construction.csproj)
- [전체 실행 안내](../README.md)

-Mode Benchmarks와 -Mode All에도 구성 측정을 포함했습니다. 결과는 verification/results/construction.json에 저장하고 반복 실행 시 덮어씁니다. 이번 별도 프로세스 재측정은 construction-repeat.json에 보관했습니다. 결과 JSON은 Git 제외 대상이며 측정 소스는 저장소에 보존할 파일입니다.

.NET 8.0.32, Windows 10.0.26300, x64, Workstation GC, Release, DOTNET_TieredCompilation=0 환경입니다. 7개 배치의 중앙값·최소·최대를 기록했습니다. 큰 모형의 실행 시간을 제한하기 위해 규모별 반복 횟수를 다르게 정했습니다.

- 노드 규모 S=N×(평면 1, 중첩 5).
- 추가·생성 경로는 비용 기준 C=N×S, 한 번 검증은 C=S.
- 배치당 반복 횟수는 clamp(524,288/C, 3, 16,384), 워밍업은 clamp(32,768/C, 2, 128)이며 정수 나눗셈을 사용합니다.
- 예를 들어 평면 1,024개와 중첩 직접 자식 512개 구성은 워밍업 2회, 배치당 3회입니다. 각 배치의 정확한 횟수는 JSON에 있습니다.
- 대조군은 워밍업 2,000회, 배치당 100,000회입니다.

할당은 GC.GetAllocatedBytesForCurrentThread로 측정했고 무작업 0 B/회, byte[64] 생성 88 B/회 양성 대조를 확인했습니다. 한 프로세스에서 모형을 순서대로 측정한 뒤 별도 프로세스에서 반복했습니다. 교대 비교나 통계적 유의성 검정은 수행하지 않았습니다. GC 수집은 측정 구간 밖에서 수행했습니다.

두 실행의 63개 항목은 모든 할당 값이 일치했고 배치별 할당 값도 안정적이었습니다. 풀 최초 대여·용량 증가 비용은 워밍업에서 제외되므로 fresh도 차가운 풀에서 처음 구성하는 비용은 아닙니다. CPU 시간과 객체 크기는 호스트·런타임에 따라 달라지며 Unity Editor·Mono·IL2CPP·Player 결과는 아닙니다.

라이브러리 MVID는 09c4fac9-b8f8-4cb6-aeca-cfc1d29d0e0a입니다. 캐시된 패키지를 사용하는 오프라인 옵션으로 측정하여 해당 실행의 NuGet 취약성 감사는 생략했습니다. 구성 프로젝트와 전체 Verification.slnx 빌드는 경고 0개·오류 0개였습니다. 기존 동작 검증 69/69·로그 72/72는 앞선 순회 비교 단계의 결과이며 이번 측정 때문에 재실행하지 않았습니다.

이번 변경은 벤치마크·실행 스크립트·검증 솔루션·문서입니다. ConditionGroup 등 운영 C# 소스는 수정하지 않았고 새 API나 성능 최적화는 적용하지 않았습니다.
